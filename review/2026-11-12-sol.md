# Sol review: implementation findings

Reviewed the frozen `DESIGN.md` at `f4ce2e6` and testbed code at `1c2631d`, against `2026-11-12-implementation-findings.md`. No changes to the draft. Proposed wording below is for Jesper to decide.

The strongest findings are cancellation/recovery, tombstone isolation, late-write loss, and split-record publishing. Empty inventory entries are a canonicalization preference; the unknown-version attack is an availability limitation within the stated threat model. Passing the proofs does not establish that the SDK implements their definitions: the tombstone counterexample below demonstrates that distinction.

## Numbered findings

**1. Real; amend the proposed fix (§8.2, §11.6–11.7).** The restart and pre-announcement checks are necessary. But “exported” is the wrong permanent boundary: an uploaded draft is exported and §11.7 expressly permits discarding it. The home note exposes the ID, key and intended change, not necessarily the signed statement itself. Use *announced*, and distinguish an uncertain acknowledgement from an absent write.

> Persist the exact signed statement before exporting it. While a change remains pending, retries reuse that statement. An unannounced draft may be discarded under §11.7; an announced statement must never be replaced or withdrawn. After a full sync, resume an observed announcement, or an own pending note whose parent is still the head. With no own note, resume an unexported journal only if its parent is still the head and no other note is present; otherwise cancel it and tell the user. Immediately before announcing, sync again and require the expected note and parent, unless the statement is already announced.

This reduces avoidable forks; it cannot close the check-to-append race already accepted in Q20. A local `NoteWritten == false` is **not** evidence that home received nothing; see additional finding B.

**2. Real specification gap; agree with a typed register (§9.2–9.3).** “Sticky forever” conflicts with a generic field-only pruning rule. Define the complete partition, not just an empty field name:

> Register keys are `(assign, record, fieldBytes)`, `(set, record, fieldBytes, elementBytes)`, and `(delete, record)`. Supersession and context/base construction operate only within one register. A delete has an empty field name, no value or element, and can be superseded only by another delete. It does not discard other fields' writes.

Use a distinct operation discriminator, not a reserved-looking field string; the current Go implementation has a collision (A below). This also settles G-37 and mixed register/set operations on one field name.

**3. Real interoperability clarification; agree (§5.5, §9.4, §11.6).** Verified independently in the conformance work.

> A logical write or statement is identified by `H(sigInput)`. Two signatures over the same input identify one write. A roster conflict requires different statement IDs with the same parent. Signing again produces the same signature input and write ID; signature bytes need not match. Durable retries reuse the stored signed message.

Envelope hashes still identify physical messages for transport/GC; do not replace that distinction with write-ID-only message GC.

**4. Safe canonicalization preference, not a demonstrated security defect (§8.3).** The signed commitment fixes the exact bytes, so empty entries do not make receivers authorize different writes. The encoding is unique for a map that distinguishes an absent record from an empty record; Lean instead models a set of pairs. Aligning them is sensible:

> Each listed record MUST have `writeCount > 0`; a zero-write entry is invalid. The empty inventory is exactly `u32(0)`.

Update the generators, parsers and model together; do not describe the old allowance as a hash or authorization break.

**5. Agree as a necessary validity clarification (§8.3).** Local transition validity is insufficient; the Go `chainValid` interpretation is correct.

> The referenced statement and every ancestor through the pinned genesis MUST be valid. Missing ancestry holds the write; an invalid ancestor rejects it. An unannounced draft cannot authorize ordinary data publication.

Owner signatures on invalid branches remain fork evidence under §9.4, not data authority.

**6. Encoding gaps: confirm the seven existing choices, with two replacements (§5–7, §10–11).** Add explicit normative wording:

* §5.4: the AAD tag is its **32 ASCII base32 characters**, not the decoded 20 bytes.
* §7.1: genesis has `n = key.n = 0` and a `nonce` containing exactly 16 random bytes in canonical b64u. Require this in genesis validation.
* §6.2: collection/invite IDs in home record names use canonical b64u, with the shown literal prefixes.
* §11.4: `have` is the 32-byte ID of the latest valid roster statement held, not an epoch counter or commitment.
* §10.5: JSON vectors may be unordered; reject repeated devices, then sort decoded device bytes for signing and merge.
* §10.5: `v` occurs exactly on assign; `e` exactly on add/remove. Other operations sign the empty value. Do not confuse an omitted field with a required empty value.
* §9.1: millis outside `[0, 2^48)` are invalid despite the wider signature slot.
* §6.3/§10.5: specify `type = pairreq | pairchallenge | pairreply`. Requests contain `name, ek`; challenges `ek, n, sig`; replies `ek, sealed`, where `sealed` is b64u of `enc || ct` over the raw 32-byte US, wrapped in the existing kind-3 envelope. Keep the existing signature inputs, HPKE info and AAD.
* §7.3: replace the blanket `_name` requirement: fixed `_roster` and `_meta` names are implicit in their IDs. Dynamically named home records carry a signed UTF-8 `_name` whose derived ID matches their record ID. Requiring a `_name` write in `_roster` contradicts its statement-only schema.

Core home **value** encodings are also missing, not merely record names; see C below.

**7. Real provider/UX incompatibility if the reported measurement holds (§10.2, §13.1, Q1).** Choose a token per concurrently connected Fastmail device. Catch-up-only changes the promised foreground real-time behavior; a relay adds infrastructure.

> On a provider that permits one push stream per credential, each concurrently connected device requires a distinct credential. Fastmail setup, invitations and pairing must provide a separately issued token for the new device, rather than copying the inviter's token. Tell the user when separate credentials are required or live updates are unavailable.

Treat this as measured provider behavior, not a universal JMAP rule. I did not rerun the live account. The cited `fastmail_test.go` currently tests one watcher, not the same-token/different-token interference experiment; retain that experiment as a repeatable regression before relying on it as a provider contract. [RFC 8620 §7.3](https://www.rfc-editor.org/rfc/rfc8620#section-7.3) permits multiple EventSource connections.

## Scenario gaps

**G-06 — Real liveness failure (§11.5).** Neither “current epoch only” nor “also the immediately previous epoch” handles arbitrarily delayed delivery safely. Membership continuity is the relevant boundary:

> Accept a signed leave notice when `at` is on the current valid chain, lists its signer, and that signer remains listed continuously from `at` through the head. Epoch changes alone do not invalidate it. Removal followed by readmission invalidates notices from the earlier stay. Removal still requires the owner's confirmation.

**G-26 — Real silent-loss case; reject the suggested vector fixes as written (§9.2, §11.6).** Reproduced with validly signed writes. A snapshot write claiming `{M:100,A:100}` causes an honest new-epoch base to cover A's unseen old write. Capping that base prevents it from covering the poisoned snapshot write's `reach`, so ordinary honest replacement no longer settles the field. Removing the original author's claims also misses poison copied into honest descendants.

Minimal safe v1 wording, using the existing app-recovery path:

> Claimed vectors are not proof of delivery. An own write absent from the inventory that is not signed again solely because the new state supersedes it MUST be retained as potentially unshared work and surfaced to the app for recovery or explicit dismissal. Removal restores future editing; it does not establish that all old-epoch edits were delivered.

Cost: recovery may show a genuinely obsolete edit. Stronger automatic recovery without that ambiguity needs additional causal evidence; do not silently change base construction and reuse the existing proofs.

**G-01 — Real cleanup/key-lifetime omission, not a demonstrated US disclosure (§6.3).** The stored reply remains HPKE ciphertext.

> After durably installing US, the new device MUST erase its ephemeral private key and pairing secret and SHOULD destroy the session's messages. On abandonment or expiry it MUST erase both secrets; the showing device SHOULD remove expired session messages. Do not delete an approved reply before the new device can consume it.

No extra confirmation message is needed for cleanup performed by the successful recipient.

**G-49 — Real request liveness omission within the accepted availability threat (§11.2, §6.3).** Best-effort healing currently excludes these channels.

> While a join or pairing attempt is valid, its sender retains the request and re-publishes the same request after a full sync finds it missing, until completion or expiry. Receivers deduplicate retries, including requests already declined. Expiry stops retrying; nothing runs forever on a timer.

An actively deleting hub can still prevent completion; narrow §12.2's “temporary nuisance” claim accordingly.

**G-09 — UX/state omission, not authorization failure (§6.2, §11.3–11.4).** Refusal hints cannot become authenticated decisions just because more reason codes exist.

> For closed, exhausted or expired invites, the owner SHOULD send the existing unavailable/declined hint. On local expiry the joiner stops retries and waiting UI, but retains the requested membership, invite and owner pin so a delayed valid grant can still arrive. Explicit cancellation sets `left` and rejects later grants. A decline hint alone never finalizes the request.

Avoid adding an `expired` state without also updating §11.4's grant acceptance states.

**G-37 — Correct clarification (§9.2).** The set paragraph already says each element has its own register, but the construction paragraph should explicitly say “the kept writes of the register being edited.” Use item 2's typed partition. A `cake` dot must not enter a `balloons` remove's context.

**G-40 — Real non-quiescence/fragmentation gap; do not adopt unrestricted set-of-messages GC (§10.6–10.7).** With messages `{a,b}`, `{b,c}`, `{a,c}`, each is covered by the other two; concurrent union-based deletion can remove all three. Deterministic splitting alone does not establish safe replacement across layouts.

Minimal safe v1 text:

> Publish for healing only if the union of valid hub fragments does not dominate the local kept state. Incomparable fragments alone do not trigger publication. Retain the existing single-message domination and hash-order GC rule. Split records may retain overlapping fragments; convergence to one hub message is not promised for them.

Trade-off: weaker compaction, preserved quiescence and GC safety. A stronger compactor needs its own replacement-order proof, not a wording-only change to domination.

**G-60 — Real persistent availability attack; not an E2EE/authorship break (§15, §12.2).** One unsupported message can suppress healing even after the attacker stops deleting. This fits the availability exclusion, but contradicts an unconditional self-healing claim. My preferred v1 rule:

> Within a v1 epoch, leave unsupported-version messages untouched, but let only authenticated v1 messages affect v1 processing, healing and GC. No in-place cross-version migration is defined until a v1-authenticated channel-retirement transition is specified.

This gives up §15's currently unspecified migration promise. Keeping today's guard is also defensible if the persistent denial and manual recovery requirement are explicitly accepted. Reject conflicting header/envelope versions as malformed; neither should freeze a channel by itself.

**G-20 — Real durability requirement (§9.1, §17).** “Strictly increasing” already implies this across restarts; specify how it is achieved:

> Durably reserve each new HLC and persist the corresponding write before acknowledging the edit or exporting it. A restart must never reuse an exported dot. If the local high-water mark cannot be recovered, generate a fresh device ID before writing. Do not recover it from other users' claimed vectors. The app and extension share this reservation under their existing lock.

## Additional findings

**A. High: the implemented delete register aliases a valid field.** `sdk/go/merge.go:39–46` uses `"\x00delete"` as its private slot name. An assign with that field and a context covering the tombstone gets the same slot, prunes the delete, and resurrects the record. Escaped NUL is valid JSON/UTF-8; I reproduced this with signed writes accepted by `ParseKind1`. Use an explicit slot-kind discriminator. Lean's algebraic slot type does not have this collision, so its sticky-tombstone theorem does not cover this Go representation.

**B. Medium: a lost home-note acknowledgement defeats the new resume fix.** `sdk/go/device/rotate.go:401–415` handles `!NoteWritten` before an observed own note. I injected a successful home append followed by an error, reopened the device and called `Resume`: it deleted its journal while its own note remained, and subsequent sharing changes returned `ErrPending`. Check the observed own note before the local acknowledgement flag. Add this uncertainty boundary to the crash cases; existing panic hooks occur after acknowledgements.

**C. Real wire gap: independent home formats already disagree (§6.2, §10.5).** `conformance/journal.py` uses flight fields `id/key` and JSON `null` to clear it; Go's `Note` uses `stmt/k`, and Go clears it with zero-length value bytes. Worse, `device.go:234` decodes `null` into a zero-valued `Note` and treats it as pending. Primitive-vector agreement does not cover home interoperability.

> Specify the byte encoding of every protocol-defined home field. For `flight`, choose one schema, e.g. UTF-8 JSON `{parent,stmt,k,members}` with 32-byte b64u IDs/key, and literal JSON `null` for no pending change. Reject malformed objects and interpret null as absent. Specify scalar/keys/invite encodings as well; they are protocol fields, not app-defined opaque values.

The particular spelling is a preference; publishing a complete schema and testing one SDK's home through the other is required.
