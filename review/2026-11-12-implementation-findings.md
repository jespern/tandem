## Findings that need a decision

For each: is it real, and what exact text would fix it? Say so if you think the fix is wrong.

### 1. Resuming an unexported key change kills the collection (§8.2, §11.6, §11.7)

Reproduced by `TestCrashThenSecondDevice/2:journal`:

1. Device A of the owner journals its signed epoch-starting statement `S_A` (step 2) and crashes before writing the `flight` note to home.
2. Device B sees no note, so §8.2 lets it change the roster. It signs and announces `S_B` with the same parent.
3. A restarts. §8.2/§11.6 say it "resumes with those bytes": it writes its note, uploads, and announces `S_A`. Two announced successors: dead (§9.4).

The same race exists without a crash when B discards A's note (§11.7 "Otherwise the change never happened") while A is merely slow: A reaches step 4 and announces (scenario gap G-08).

**Fix implemented in the Go engine** (proposed text):
- Signed bytes that have **not been exported** may be dropped. On restart, a device that hadn't yet written its note uses its journalled statement only if the statement's parent is still the roster's head and no other device's note is present; otherwise it drops the journal and tells the user that nothing changed.
- Immediately before announcing (step 4), a device syncs and checks that the note in home still names its statement and that the parent is still the head. If not, the change was discarded or overtaken: it destroys what it uploaded and drops the change. This narrows, but can't close, the window §11.7 already accepts.

Question: is "never abandons signed bytes it has exported" the right boundary, given that the note itself is what exports them?

### 2. Which register a `delete` belongs to (§9.2; Lean finding F1; scenario gap G-28)

§9.2 doesn't say which writes a `delete` competes with. `model/owner_model.py` keys registers by (record, field), so a later `assign` to the delete's field whose context covers the delete supersedes it and the tombstone disappears (`tombstone_dropped_if_keyed_by_field` in `proofs/`). Lean and the Go engine give deletes a register of their own: only a delete supersedes a delete. The encoding of a delete (its field name) is also unspecified. Proposed: "A delete write has an empty field name and forms a register of its own; only another delete can supersede it."

### 3. Randomized signatures (§9.4, §11.6)

CryptoKit's Ed25519 is randomized (verified on macOS 27.2; Codex found the same). Signing the same `sigInput` twice gives two signatures and one write ID. §11.6's "every device … gets the same bytes" holds for `sigInput` and the write ID, not the signature; §9.4's "two different successors" must mean two different statement IDs. Proposed: say so in both places, and that writes are deduplicated by write ID, never by signature or envelope.

### 4. Inventory entries with no writes (§8.3; Lean F3)

The canonical format allows a record with zero writes, so two inventories listing the same (record, write) pairs can have different bytes and hashes. Proposed: every entry lists at least one write.

### 5. "A valid roster statement" (§8.3)

Validity (§8.2) is relative to the parent. A statement can be valid relative to an owner-signed but invalid parent. Proposed: data names a statement whose whole chain back to the genesis is valid.

### 6. Bytes the vectors had to choose (see `vectors/README.md`)

The AAD carries the tag as its b32 text; the genesis numbers `n` and `key.n` from 0 and carries its 16 random bytes as `nonce`; home record names spell IDs in b64u; a key request's `have` is a 32-byte statement ID; vectors may arrive in any JSON order but name a device once; `v` only on assign and `e` only on add/remove; HLC millis at or above 2^48 are invalid. Also unspecified: pairing request, challenge and reply share a channel without a `type` field, and the reply's JSON isn't given; whether named records (`_roster` included) really carry a `_name` write. Please confirm or replace each.
