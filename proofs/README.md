# Tandem proofs and reference model (Lean 4 + Mathlib)

**Status:** proved against `DESIGN.md` on `design/admin-key` (participants and devices, sharing from the hub directory, the hub password; 2026-11-13). Until then it was proved against the frozen first draft (`main` at `f4ce2e6`); the § numbers below are the current design's. Nothing is left as `sorry`, and no axioms are added. The same definitions run as the test oracle, `tandem-oracle` (`ORACLE.md`).

```sh
lake exe cache get          # once: prebuilt Mathlib (~7 GB in .lake/, git-ignored)
lake build                  # the proofs
lake env lean Audit.lean    # reject unfinished proofs and nonstandard axioms
lake build tandem-oracle    # the oracle (first build compiles Mathlib's C, ~2 min, ~0.5 GB)
python3 -B difftest.py      # oracle vs model/owner_model.py on random histories
```

Pinned to Lean 4.35.0 and Mathlib `v4.35.0`.

`Audit.lean` checks transitive axiom dependencies, not just the source text. It permits
Lean's standard `propext`, `Classical.choice` and `Quot.sound`; any dependency on
`sorryAx` or a custom axiom fails the check.

## What is proved

The logic is proved: merge rules, roster rules, garbage collection, encodings. The cryptography is assumed, not proved (§ Assumptions).

| `Kept` | Under **any** strict partial order:<br>• the kept set of a union is the kept set of the union of kept sets (`kept_union`);<br>• merging is commutative, associative and idempotent (`merge_comm`, `merge_assoc`, `merge_idem`);<br>• delivery order, grouping and duplicates never matter (`receive_of_perm`);<br>• replaying a superseded write changes nothing (`kept_insert_superseded`). | §9.3 | proved |

The record-state instances of `Kept` follow. | §9.2, §9.3 | proved |
| `Record` | **Sets:**<br>• an add that nothing supersedes keeps its element (`add_wins`, `add_remove_concurrent`);<br>• a remove that saw the adds removes the element (`remove_supersedes_seen_add`, `absent_of_all_adds_superseded`);<br>• a replayed add stays out.<br>**Tombstones** are sticky under merge (`deleted_sticky`, `kept_delete_stays`).<br>**A delete supersedes what it includes**, in any field (`delete_supersedes_seen_other_field`); one built over the record's state leaves only itself (`delete_built_over_state`, `state_only_deletes`); a concurrent write survives under it (`concurrent_write_survives_delete`). A same-epoch statement keeps every staying participant's device-policy floor; a new epoch may set new ones.<br>**What a device follows and whether the collection is dead are functions of the set held:**<br>• order and duplicates don't matter (`same_set`, `same_set_perm`);<br>• once dead, dead in every superset (`dead_mono`);<br>• every device holding both conflicting statements and the parent's line agrees (`dead_of_held`, `conflict_agreed`);<br>• unannounced drafts change nothing (`drafts_change_nothing`). | §8.2, §9.4, §11.6 | proved |
| `Eligibility` | Eligibility never changes once the statement a write names and the epoch start are followed, while the collection is alive (`eligible_stable`, `eligible_mono`).<br>• Readers can't write (`reader_rejected`).<br>• Only the owner writes `_meta` (`meta_owner_only`).<br>• `delete` on a named record is invalid (`named_delete_rejected`), and so is one with a field, element or value (`malformed_delete_rejected`).<br>• Without the inventory, only writes whose source epoch is exactly `E`, signed under a policy snapshot that extends the author's floor, count (`without_inventory`).<br>• A write below the floor enters only through the fixed inventory (`below_floor_only_by_inventory`).<br>• A clock past 2^48 ms makes a write invalid (`clock_overflow_rejected`). | §6.9, §7.3, §8.3, §9.1 | proved |

| `VectorLimit` | A write built from the kept writes it governs supersedes all of them, given a fresh dot (`build_supersedes`). Writes over the limit are invalid (`over_limit_invalid`). | §9.2 | proved |

## Findings

**F1. A delete's register — resolved: delete supersedes what it includes (decided 2026-11-12).**
- **The gap:** §9.2 didn't say which field a `delete` names, or whether an `assign` (or `add`) can supersede a `delete`. Keyed by (record, field), as `model/owner_model.py` is, a write to the delete's field that covers it drops the tombstone (`tombstone_dropped_if_keyed_by_field`).
- **The decision** (Jesper, on Fable's review `review/2026-11-12-fable.md` §2):
  - a delete has an empty field name, no element and an empty value; its context and base are built over all kept writes of the record, in every field;
  - a delete supersedes any write to its record that it includes, whatever the field or op (same epoch: includes and isn't included; later epoch: its base covers `reach(x)` and `x.base`);
  - only a delete supersedes a delete;
  - registers are otherwise (record, field) for `assign`, (record, field, element) for `add`/`remove`.
- **What the Lean model does:** `Write.slot` is unchanged; `Write.governs` adds a delete's reach over its record, and `sup` uses it. A malformed delete is invalid (`malformed_delete_rejected`).
- **What is proved:** supersession is still a strict partial order for any vectors (`sup_strict`), so merge is still a join; tombstones are sticky (`deleted_sticky`, `kept_delete_stays`); a delete built over the record's state leaves only itself (`delete_built_over_state`, `state_only_deletes`), the "one small message per deleted record" of §12.3; a write concurrent with the delete stays kept under it (`concurrent_write_survives_delete`); records without deletes merge exactly as before (`state_of_undeleted`), so display and sets are unaffected.
- **Still to do outside `proofs/`:** the §9.2 text and the Go `slotOf`.

**F2. Our plan, not the design, was wrong about signing again.**
- **The plan's claim:** "a re-signed write never supersedes a write the snapshot kept". It is false.
- **Why it's false, and why that's right:** a late write that replaced a snapshot write in the old epoch replaces it again once signed in the new one (`late_write_replaces_snapshot_again`). That is correct behaviour, and §11.6 never claimed otherwise.
- **What holds instead:** the theorems in `Reissue`.

**F3. Inventory entries with no writes (§8.3) — resolved: §8.3 now says every entry lists at least one write and a zero count is invalid.**
- **The gap:** the byte format allows a record with a write count of zero, and `model/owner_model.py` emits one for `{rec: []}`. The bytes are then not a function of the set of (record, write) pairs: `{a: [x]}` and `{a: [x], b: []}` list the same writes under different commitments.
- **Why it's harmless:** every device judges against the committed bytes.
- **The cost:** the bytes stop being canonical. A device resuming from its journal must reuse the exact bytes, as §11.6 already requires.
- **What the Lean model does:** `Enc.canon` never emits an empty entry. `difftest.py` doesn't generate empty entries, so it doesn't test this case.
- **Suggested fix:** say in §8.3 that every entry lists at least one write.

**F4. Two slips in §5.5 — fixed on `design/admin-key` (6da1f4b).**
- The `sigInput` comment called `hubID` the "pinned recovery public key"; it is `pub(MKs)` (§5.3).
- §5.5 said the other signed objects' `TANDEM-…-V2` prefixes are "given where they're defined"; none is defined yet. They are part of Q28, and `Enc.signedTags` holds only the two fixed so far (`TANDEM-WRITE-V2`, `TANDEM-ADMIN-CAPSULE-V2`).
- The same stale recovery-key description of `hubID` in §13.1 was corrected to `pub(MKs)` in `2447186` on `design/admin-key` (also applied on this branch).

**F5. May a member's display name change? (§8.2) — open.**
- **The gap:** the first draft required every staying member's `uka`, `name` and `via` to stay the same. The current text keeps only "the same participant ID", which is trivially true, and calls names display hints. So whether a same-key statement that only renames a member is valid isn't said, and that decides which statements are valid, and so which successors count for the conflict test.
- **What the Lean model does:** names may change, in any statement (`Examples`: a rename is followed). Requiring them to stay is a one-line change in `stepOK`.

**F6. Signing again an own write that a later own write replaced (§11.6) — resolved: §11.6 amended and both engines aligned (decided 2026-11-15).**
- **The gap:** §11.6 signs again an own late write that "no listed write supersedes". Two own writes that both missed the inventory, one replacing the other, are therefore both signed again and come back as a conflict (§11.6, last paragraph). A device that dropped the replaced one early (`GC.md` §2) signs only the later one, so its outcome differs (`listed_rule_differs`).
- **The proposal:** do not sign again an own write that a later own write the device holds replaces; the later one, signed again or listed, carries the change. That removes the conflict, and with it dropping is invisible (`resign_same`).
- **The engines differ from both:** Swift and Go do not sign again an own write that *any* write they hold replaces, unless that write's claim about this installation is forged ("every write seen of the record counts"). An own late write replaced only by a write the inventory doesn't list, such as a removed member's late edit, is then lost silently where §11.6 signs it again. Under that rule `resign_same` fails too: a dropped write's replacement may be one whose claim is forged.
- **The decision** (Jesper): §11.6 now says an own write that a later own write replaced is not signed again, and that the decision waits until every listed write of the record is held. A write of the new state replaces a late write too: a listed one or one written in the new epoch (fixed the same day, found by the browser device's test of a forged claim). `resign_same` takes the replacing writes as a parameter, so it covers both. Both engines follow it: a later own write, or a listed write whose claim isn't forged, keeps a write from being signed again; nothing else does (`TestRotationOwnWriteReplacedOnlyByAnUnlistedWriteIsSignedAgain`, `testOwnWriteReplacedOnlyByAnUnlistedWriteIsSignedAgain`).

## Assumptions

1. **Symbolic cryptography.**
   - A statement or write is its content, and its ID is collision-free.
   - The roster/write oracle represents a signature by its participant's name and assumes an admitted signing device. `Registry` separately models certificates, revocations and policy-snapshot extension (§6.9); the oracle does not run that registry validator. Whether a write's source snapshot extends a floor remains a fixed relation supplied from outside (`Records.ext`). Signatures, hashes and device-key possession proofs are assumed valid for the named content; their wire verification is not modelled.
   - New-member invitations use the manager's pre-signed capability and an invite-key-signed claim. `Invitation.accept` checks the capability's hub, purpose, signer and claim reference; it neither holds the management secret nor creates a fresh manager signature. Expiry and cancellation are checked against supplied local time/state, not globally authoritative mailbox state.
   - `Receipts` takes admitted admin/member signer predicates as inputs and identifies pairing claims by participant and target keys. The complete certificate/delegation/package binding of a release, the collection context and HPKE sealing of sharing receipts, and event-ID deduplication remain wire-validation obligations. `HomeRekey` is conditional on the supplied remaining-device set excluding the attacker and on a fresh new key; it does not implement the registry-to-rekey procedure.
   - An admin capsule is signed with `MKs`, so only the management key adds one, and a copy of a capsule is that capsule (its ID is its hash).
   - **Perfect cryptography for secrecy** (`Symbolic`): ciphertexts reveal nothing without their key, derived keys can't be inverted, HPKE opens only with the private key. A password the attacker hasn't got is one it can't guess: Argon2id's cost (§6.7) is what makes that reasonable for a good password, and nothing here measures it. A private key derived from a seed (`MKa` from `MS`) is given explicitly to whoever holds the seed.
   - Unicode NFC and UTF-8 length are functions given from outside (`HubPassword.Text`); only their being functions of the code points is used.
   - A statement carries its ancestry (`Stmt` is the list of nodes, nearest first), as its ID commits to its parent's.
2. **Supersession compares epochs by their counter**, as `owner_model.py` does. On one roster line the counter and the epoch-start ID determine each other.
3. **Byte-identical copies (§10.7).** The device that made an envelope never removes a copy on account of a copy it has itself already removed: it sees its own destroys. Every other destroy may act on a stale view. Its justifying message must only have been on the hub at some point.
4. **Not modelled:**
   - the six-step rotation procedure, grants, key requests and the `flight` note. These are procedures; `owner_model.py` simulates them, and the scenario suite will exercise them on the testbed;
   - the invitation capability's encoding, consumption and propagation of cancellation (Q28), the activity history's records (§6.10), and the home re-key's ordering and crash recovery;
   - freshness: a device judges the objects it holds; withholding by the mailbox is not solved (§6.9);
   - the mail bindings;
   - JSON and `b64u` strictness (§10.5), which are the SDKs' job, with test vectors;
   - Argon2id itself and the real AEAD (`conformance/test_admin_capsule.py` checks those with real cryptography, `conformance/test_pairing_gate.py` the pairing gate).
5. **Unprefixed hashes:** `H(value)`, `H(inventory bytes)`, `H(envelope)`. They hash data that is never read as another domain's input.
